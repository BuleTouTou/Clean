# 后续优化点：上线部署与小牛看房系统对接

## 1. 背景

当前项目已经具备房源文件清洗、人工审核和 Excel 导出能力，但仍然是本地文件处理模式。上线后，清洗完成的文件需要继续提交到小牛看房系统，避免用户手动下载、切换系统和再次上传。

确定的目标流程：

```text
用户上传原始房源文件
        ↓
平台完成清洗、审核和导出
        ↓
前端通过本项目后端获取店铺列表
        ↓
前端弹窗选择店铺名称
        ↓
前端向本项目后端提交店铺 ID 和任务 ID
        ↓
后端将清洗文件上传到与小牛共用的 OSS
        ↓
后端获得文件 URL
        ↓
后端调用小牛接口提交 store_id + file_url
        ↓
返回远程调用任务号、结果和错误信息
```

## 2. 总体原则

- 前端只负责展示店铺、发起清洗和提交动作，不接触 OSS AccessKey。
- 所有小牛系统接口调用由后端完成，避免在浏览器暴露第三方凭证。
- 店铺选择使用稳定的 `store_id`，名称和编码只用于展示、检索和审计。
- 文件上传到共用 OSS 采用流式或分片方式，避免将完整大文件一次性读入内存。
- 文件和店铺提交状态需要持久化，支持失败重试和结果查询。
- 平台与小牛使用同一个 OSS Bucket 或同一套 OSS 访问域名；对象仍应按私有权限管理。提交给小牛的 URL 必须符合小牛接口约定，可使用受控的签名 URL 或小牛可访问的内部 URL。
- 对接层与清洗核心解耦，后续可以替换小牛系统或增加其他房源系统适配器。

## 3. 店铺数据接口

### 3.1 本项目提供给前端的接口

平台后端提供统一接口给前端：

```http
GET /api/stores?keyword=朝阳&status=active&page=1&pageSize=50
```

响应示例：

```json
{
  "items": [
    {
      "id": "store_123",
      "name": "北京链家朝阳望京店",
      "code": "BJ-CY-WJ-001",
      "status": "active"
    }
  ],
  "total": 1,
  "page": 1,
  "pageSize": 50
}
```

前端弹窗至少展示：

- 店铺名称 `name`
- 店铺编码 `code`（如果小牛系统提供）
- 当前状态 `status`

真正提交时使用 `id`，不要使用店铺名称作为业务主键。

### 3.2 后端获取店铺数据的逻辑

后端接口收到前端查询请求后，调用小牛看房系统的店铺列表接口，再将结果转换为本项目统一格式返回。前端不直接调用小牛接口。

推荐逻辑：

1. 前端请求 `GET /api/stores`。
2. 后端携带服务端 Token 调用小牛店铺列表接口。
3. 后端提取并返回 `id`、`name`、`code`、`status`。
4. 前端只保存用户选择的 `id`，名称和编码作为展示快照。

如果小牛接口性能较慢，后端可以增加短时缓存，但缓存不是数据的最终来源；店铺列表的权威来源仍然是小牛接口。

同步表建议包含：

| 字段 | 说明 |
| --- | --- |
| `id` | 小牛系统店铺 ID，唯一主键 |
| `name` | 店铺名称 |
| `code` | 店铺编码，可为空 |
| `status` | 是否可用 |
| `source_updated_at` | 小牛侧更新时间 |
| `synced_at` | 平台同步时间 |
| `raw_payload` | 原始响应，便于排查字段变化 |

## 4. 确定的文件上传和远程提交方案

本项目采用“后端上传共用 OSS，再调用小牛接口提交 URL + 店铺 ID”的单一路径：

```text
清洗文件
  ↓
平台后端以流式方式上传 OSS
  ↓
获得 object_key / url / etag
  ↓
向小牛提交 store_id + 文件地址
```

### 4.1 完整流程

```text
前端选择店铺
  ↓
提交 task_id + store_id 到本项目后端
  ↓
后端读取已生成的清洗文件
  ↓
后端流式上传到与小牛共用的 OSS
  ↓
获取对象 URL、object_key、etag、sha256
  ↓
后端调用小牛“文件导入/提交”接口
  ↓
提交 store_id + file_url
  ↓
记录小牛返回的任务号和处理状态
```

### 4.2 本项目提交接口

```http
POST /api/tasks/{task_id}/submit-to-niux
Content-Type: application/json

{
  "store_id": "store_123"
}
```

前端不上传第二份文件，也不传 OSS AccessKey。后端根据 `task_id` 找到已经生成的清洗文件。

### 4.3 后端调用小牛接口

```http
POST https://niux.example.com/api/house-files/import
Authorization: Bearer <server-side-token>
Content-Type: application/json

{
  "store_id": "store_123",
  "file_url": "https://shared-oss.example.com/housing/2026/08/task_abc/sale.xlsx",
  "file_name": "售房清洗导入_20260830_120000.xlsx"
}
```

字段名称以小牛真实接口文档为准；如果小牛接口使用 `url`、`fileUrl`、`file_id` 或其他名称，应在适配器中转换，前端接口不跟随第三方字段变化。

### 4.4 OSS 对接要求

平台使用与小牛相同的 OSS 账号、Bucket 或访问域名时，需要确认：

- 小牛服务端是否能访问该对象 URL。
- URL 是公网 URL、内网 URL，还是带签名的临时 URL。
- 签名 URL 的有效期是否覆盖小牛异步处理时间。
- 小牛读取文件时是否需要特定的 Content-Type、对象元数据或路径格式。
- 小牛要求提交完整 URL，还是只要求 `object_key`。
- 文件上传完成后由谁负责删除对象。

不应默认把 Bucket 设置为公共读。若小牛异步读取文件，优先使用满足其网络环境和有效期要求的受控 URL；必要时延长签名 URL 生命周期，或采用小牛认可的内部访问地址。

### 4.5 平台内部文件记录

```http
平台内部记录（不直接暴露给前端）：
Content-Type: application/json

{
  "task_id": "task_abc",
  "store_id": "store_123",
  "object_key": "housing/2026/08/task_abc/sale.xlsx",
  "file_url": "https://oss.example.com/housing/2026/08/task_abc/sale.xlsx",
  "filename": "售房清洗导入_20260830_120000.xlsx",
  "size": 183420,
  "sha256": "..."
}
```

### 4.6 查询远程提交状态

```http
GET /api/tasks/{task_id}/niux-submission
```

## 5. 推荐的业务接口

### 5.1 查询店铺

```http
GET /api/stores
```

### 5.2 提交清洗结果

提交请求只需要 `store_id`。后端自动完成 OSS 上传和小牛远程调用。

响应示例：

```json
{
  "status": "success",
  "store_id": "store_123",
  "niux_task_id": "upload_task_456",
  "filename": "售房清洗导入_20260830_120000.xlsx",
  "submitted_at": "2026-08-30T12:00:00+08:00",
  "error": null
}
```

状态建议包括：

```text
pending → uploading → submitted → processing → success
                         └──────→ failed → retrying
```

## 6. 后端模块建议

建议新增以下模块，不要把第三方调用直接写进 `core.py`：

```text
backend/
├── app.py
├── core.py
├── api/
│   ├── stores.py              # 店铺查询接口
│   └── integrations.py        # 对外提交接口
├── integrations/
│   └── niux/
│       ├── client.py          # 小牛 HTTP 客户端
│       ├── models.py          # 小牛请求/响应模型
│       └── uploader.py        # 流式上传、分片和重试
├── storage/
│   ├── base.py                # StorageBackend 接口
│   ├── local.py               # 本地开发存储
│   └── oss.py                 # 生产 OSS 存储
└── repositories/
    ├── stores.py              # 店铺缓存/数据库
    └── submissions.py         # 提交记录和状态
```

推荐抽象：

```python
class NiuxClient:
    async def list_stores(self, keyword: str | None = None): ...
    async def commit_file(self, store_id: str, file_url: str, filename: str): ...
    async def get_submission(self, niux_task_id: str): ...
```

## 7. 数据库和任务记录

上线后不能只依赖当前进程内的 `TASKS` 字典。至少需要持久化：

- 清洗任务 ID、用户、原始文件和导出文件引用。
- 选中的 `store_id`、店铺名称快照和店铺编码快照。
- 小牛上传任务号、文件 ID、OSS object key 和提交状态。
- 请求次数、失败原因、重试次数和最后一次响应摘要。

建议使用 PostgreSQL 或其他服务端数据库保存任务状态；Redis 可用于队列和短期状态，但不应作为唯一事实来源。

## 8. 安全要求

- 小牛 Token、OSS 密钥只放服务端环境变量或密钥管理系统。
- 对店铺接口和提交接口增加登录态、权限校验和操作审计。
- 用户只能提交其有权限的店铺。
- 上传文件限制扩展名、大小、内容类型和病毒扫描策略。
- 对下载地址使用短时效签名，禁止永久公开。
- 日志中不要打印手机号、业主姓名、AccessKey、Token 或完整文件 URL。
- 对小牛 API 设置连接超时、读取超时、幂等键和指数退避重试。

## 9. 实施顺序

1. 获取并确认小牛店铺列表、文件上传、文件提交和状态查询接口文档。
2. 明确上传接口是“直接 multipart 文件流”还是“OSS 地址/文件 ID 提交”。
3. 新增店铺查询后端接口和前端选择店铺弹窗。
4. 为导出文件增加文件引用和提交记录。
5. 实现 `NiuxClient`，先在测试环境完成单文件上传。
6. 增加失败重试、幂等和提交状态查询。
7. 接入生产 OSS 或小牛预签名上传流程。
8. 最后再开放前端“一键提交到小牛”按钮。

## 10. 验收标准

- 前端可以搜索并选择有效店铺，提交数据使用 `store_id`。
- 清洗文件不会在浏览器和后端之间重复上传。
- 大文件上传过程中不会一次性读入多个完整副本。
- 小牛接口失败后，页面能看到明确状态和可重试入口。
- 同一个任务重复点击不会产生重复上传或重复导入。
- 能查询小牛返回的任务号、文件 ID 和最终处理结果。
- 敏感信息、OSS 凭证和临时 URL 不会泄露到前端或普通日志。
