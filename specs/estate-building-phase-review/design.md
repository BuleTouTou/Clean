# 小区、期名与栋座联合复核技术设计

## 1. 设计结论

采用“期名感知的栋座索引 + 小区父组 + 栋座子组 + 安全批量应用”方案。

后端仍以每个 `原始小区 + 原始栋座` 作为最终决策键，保证不同栋座可以导出不同期名；API 返回时再按原始小区合并为父组，减少前端重复展示。这样既保留现有导出流程的精确性，也不需要数据库迁移。

## 2. 模块影响

### 后端

- `backend/core.py`
  - 新增期名感知的栋座目录索引。
  - 重构小区候选生成、自动匹配和复核分组。
  - 保持栋座级决策键，增加确认方式记录。
  - 扩展规则快照和审计依据。
- `backend/app.py`
  - 在复核请求中接收每个决策键的确认方式。
  - 现有路由地址和用户权限不变。

### 前端

- `frontend/src/pages/index.vue`
  - 把楼盘审核列表改为小区父组和栋座子项。
  - 增加候选覆盖统计、安全批量应用和未解决状态。
- `frontend/src/api.ts` 与生成接口类型
  - 补充复核分组和确认方式类型。

### 测试与文档

- 增加期名唯一、跨期拆分、同栋多期冲突、无栋座兼容和旧规则回退测试。
- 更新 README 中的小区与栋座复核说明。

## 3. 数据索引设计

### 3.1 标准小区候选

每个候选保留以下身份字段：

```text
estate_id = 标准化(楼盘) + 标准化(期名) + 行政区 + 商圈
output_name = 楼盘 + 期名
```

候选不能只以 `楼盘` 去重；同一楼盘的不同期名必须是不同候选。

### 3.2 期名感知栋座目录

从 `北京-单元楼盘字典.xlsx` 建立以下只读索引：

```text
estate_phase_buildings[(标准化楼盘, 标准化期名)]
  -> {标准栋座: {标准单元}}

estate_building_phases[(标准化楼盘, 栋座核心值)]
  -> {期名}
```

匹配栋座时沿用现有优先级：

1. 标准化文本完全一致；
2. 提取楼号核心值后一致；
3. 两者都不能唯一确定时视为不兼容，而不是使用模糊结果自动确认。

字典中期名为空时，该栋座只能作为楼盘级参考，不能作为“唯一对应期名”的证据。

### 3.3 缓存

楼盘字典和栋座字典按 `文件路径 + 修改时间 + 文件大小` 生成缓存签名。文件未变化时复用解析结果；替换字典后自动失效，避免每次复核重复读取约 40 万行数据。

## 4. 匹配流程

### 4.1 行级预处理

每条原始记录生成：

```text
raw_community
raw_building
community_group_key = 标准化(raw_community)
decision_key = raw_community + 原始栋座 + 显式期名提示
```

相同 `decision_key` 的多行共享一次决定；相同 `community_group_key` 的决定在界面上合并到一个父组。

### 4.2 候选生成顺序

1. 读取栋座级已确认规则；合法且仍兼容时优先使用。
2. 原始小区明确包含期名，并且名称唯一匹配时自动确认。
3. 原始小区能确定基础楼盘，且原始栋座在字典中唯一对应一个期名时自动确认。
4. 名称候选与栋座期名交集只剩一个候选时自动确认。
5. 其余情况进入人工复核。

自动结果记录以下匹配方式之一：

```text
已确认栋座规则
楼盘加期名精确匹配
栋座唯一对应期名
名称与栋座联合唯一匹配
```

### 4.3 冲突处理

以下情况必须人工确认：

- 同一栋座在字典中对应多个期名；
- 原始小区名称对应多个基础楼盘；
- 名称候选和栋座候选没有交集；
- 栋座为空且小区名称不能唯一确定期名；
- 旧的小区级规则与当前栋座关系冲突。

系统不根据 `1–15`、`16–30` 这类连续范围自行猜测；如果字典逐栋记录能证明这种关系，则会自然得到相同结果。

## 5. API 数据结构

### 5.1 小区复核响应

`POST /api/mapping` 路由不变，`reviews` 改为分组结构：

```json
{
  "reviews": [
    {
      "key": "normalized-community",
      "raw": "示例小区",
      "rawVariants": ["示例小区"],
      "rows": [2, 3, 4],
      "buildingCount": 3,
      "unresolvedCount": 2,
      "buildings": [
        {
          "key": "原始小区｜原始栋座：1号楼",
          "rawBuilding": "1号楼",
          "rows": [2],
          "candidates": ["candidate-id"]
        }
      ],
      "candidates": [
        {
          "id": "candidate-id",
          "outputName": "示例小区一期",
          "district": "城区",
          "businessArea": "商圈",
          "compatibleBuildingKeys": ["decision-key"],
          "uniqueBuildingKeys": ["decision-key"],
          "coverageCount": 1,
          "canApplyAll": false
        }
      ]
    }
  ],
  "autoCount": 1
}
```

`candidate.id` 使用稳定候选身份，而不是只使用楼盘文字，避免同名不同期候选碰撞。

### 5.2 提交选择

保留现有 `selected` 字典，其键仍为栋座级 `decision_key`：

```json
{
  "taskId": "...",
  "selected": {
    "示例小区｜原始栋座：1号楼": "candidate-id"
  },
  "selectionMethods": {
    "示例小区｜原始栋座：1号楼": "batch-all"
  }
}
```

允许的确认方式：

```text
manual
batch-all
batch-compatible
```

后端不信任前端传来的批量范围，仍逐项验证候选是否属于对应栋座子组；无效选择返回 400。

## 6. 前端交互设计

### 6.1 视觉规格

- 目的：让审核人员先看小区整体，再处理少量冲突栋座。
- 方向：工业化工作台式的信息密度，不重做现有页面风格。
- 配色：沿用现有品牌变量 `#6510AD`、`#4F087F`、`#F4EBFB`、`#F4F7F8`、`#24132F`。
- 字体：沿用现有中文字体配置，本功能不引入远程字体。
- 布局：小区父组纵向排列；组头与候选覆盖摘要形成左右不对称信息区；展开区使用栋座明细表。

现有品牌色属于 UI 通用规范通常回避的紫色范围，但这里作为已有产品设计系统的窄范围例外继续使用，避免局部功能与全站不一致。

### 6.2 父组

父组头部显示：

```text
原始小区名
影响 N 行 · M 个栋座 · K 个待确认
[展开/收起]
```

原始小区名后直接展示栋座摘要，例如 `1号楼、2号楼、16号楼 + 8`，满足用户在不展开时也能看到栋座依据。

### 6.3 候选与批量操作

每个标准小区候选显示：

```text
标准小区名 · 城区 · 商圈
覆盖 12/15 个栋座
唯一覆盖 10 个 · 冲突 2 个
```

- `canApplyAll=true`：按钮文案为“一键匹配全部”。
- 只能覆盖部分栋座：按钮文案为“匹配兼容栋座”。
- 完全不兼容：按钮禁用并显示原因。

批量操作只填充可验证的栋座子项。用户可以在明细表继续覆盖单项选择。

### 6.4 栋座子项

每行显示：

```text
原始栋座 | 影响行数 | 推荐/已选标准小区 | 匹配依据 | 状态 | 操作
```

状态分为：自动完成、批量完成、人工完成、冲突待确认、无候选。

“保存确认并检查栋座”按钮旁显示未解决数量。允许暂不匹配，但后续导出会继续产生阻断异常。

## 7. 规则兼容与导出

- 新规则继续存入 PostgreSQL `app_settings.cleaning_rules`，不新增数据库表。
- 新规则键使用现有栋座级 `decision_key`，值升级为可兼容读取的结构：

```json
{
  "candidateId": "...",
  "outputName": "示例小区一期",
  "selectionMethod": "manual"
}
```

- 读取规则时同时接受旧字符串值和新对象值。
- 旧的小区级规则只有在无栋座或与当前栋座期名兼容时才生效。
- 导出阶段仍逐行用 `decision_key` 获取决定，因此同一小区的不同栋座可以输出不同期名。
- 规则快照增加原始栋座、候选 ID、确认方式和影响行数。

## 8. 安全与权限

- 所有复核请求继续通过现有任务归属校验，不能操作其他用户任务。
- 批量应用不新增跨任务或跨用户规则写入入口。
- 后端对每个选择重新验证，避免篡改请求把不存在的候选写入任务。
- 不在接口或日志中增加用户密码、会话令牌等敏感数据。

## 9. 测试策略

### 后端单元测试

1. 同一楼盘不同栋座唯一映射到不同期名。
2. 同一栋座对应多个期名时进入人工复核。
3. 同一原始小区的多个栋座返回一个父组和多个子项。
4. 候选覆盖全部、部分和零栋座时批量标志正确。
5. 篡改候选 ID 或把候选应用到不兼容栋座时返回错误。
6. 旧字符串规则可读取，但不覆盖冲突栋座。
7. 导出结果按栋座产生不同的标准小区期名。
8. 无栋座字段时原流程保持可用。

### 前端验证

1. TypeScript 类型检查和生产构建通过，不新增类型抑制。
2. 浏览器中验证父组折叠、栋座摘要、全部应用、兼容应用和单项修正。
3. 验证冲突项不会被错误标记为完成。
4. 验证相邻的字段映射、栋座审核和导出步骤没有回归。

### 数据字典抽样

使用真实字典只读抽样多期楼盘和同栋多期案例，不修改字典文件；业务测试数据使用合成样例，避免把真实房源数据写入测试结果。

## 10. 不需要的迁移

本设计不修改 PostgreSQL 表结构，不新增 Alembic 迁移，也不迁移历史报告。旧历史报告继续按当时保存的规则快照展示。
